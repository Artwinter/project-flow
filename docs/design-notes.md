# 设计笔记

记录几个刻意的决定，以及为什么没有做别的。

---

## 1. 为什么它这么短（约 100 行）

这个技能的定位是**入口卡**，不是知识库。

它会在几乎每次"新项目/新功能"对话里被加载。按 3000 token 一次算，
如果它承载完整规则，用户每开一个新坑就多付 3000 token 读用不上的东西。

所以切分原则是：

| 放进 project-flow | 放进下游技能 |
|---|---|
| 现在该进哪个节点 | 这个节点具体怎么做 |
| 出口是什么（gate） | 怎么通过 gate |
| 哪些坑必须绕开 | 坑的成因与细节 |

**判断标准**：这条信息会改变"下一步做什么"吗？不会的，一律不进。

---

## 2. 为什么 grill-me 和 grill-with-docs 是"二选一"

几乎所有二手教程都写成 `grill-me → grill-with-docs` 的先后关系。**这是错的。**

两者跑的是**同一套 `grilling` 访谈内核**，区别只有两点：

- `grill-with-docs` 会读代码
- `grill-with-docs` 会往磁盘写 `GLOSSARY.md` / ADR

所以串行调用 = 同一场访谈做两次，第二次会把已答过的问题再问一遍，
用户会以为 AI 没记住。

**真正的判据是"有没有仓库可写"**，不是"粗谈还是细谈"。

---

## 3. 为什么 gate 要写死

三个 gate 都是从真实事故反推的：

| Gate | 事故 |
|---|---|
| G1 谈完才往下 | spec 把"未决定"写成"已决定"，实现阶段才发现要推翻 |
| G2 接缝先确认 | `tdd` 在错误边界写测试；`code-review` 把没约定的接缝当缺陷报 |
| G3 每票清上下文 | 越往后越糊涂，最后说不清哪些决策是这票做的 |

G1 的"用户亲口说"来自 grilling 原文：
`Do not act on it until the user confirms you have reached a shared understanding.`

模型很容易在"访谈看起来结束了"时自作主张往下走。这句话把决定权交回用户。

---

## 4. 为什么保留"反模式"一节

规则说"应该做什么"，反模式说"看起来合理但其实错的事"。

后者更有信息量，因为**错误路径通常比正确路径更接近直觉**：

- "先粗后细" → 先 grill-me 再 grill-with-docs（听起来完全合理）
- "小步快跑" → 每张票都不清上下文（听起来也合理）
- "留个标记方便自动化" → 保留 `ready-for-agent`（听起来更合理）

列出五条反模式，比列出二十条规则更容易被记住。

---

## 5. 不做什么

- **不写 spec 模板**：属于 `to-spec`
- **不写访谈技巧**：属于 `grilling`
- **不写切片算法**：属于 `to-tickets`
- **不做自动化**：本技能不创建文件、不跑命令、不改代码

它唯一做的事：**在正确的时刻，把用户送到正确的技能面前。**

---

## 6. 已知局限

1. **依赖下游技能存在。** 单独装只会得到指向空处的路由表。
2. **不做依赖检查。** 如果下游缺失，需要用户自己发现。可以加一段
   "启动时检查 `~/.claude/skills` 是否存在 grilling" 的逻辑，但那会让
   加载变慢，权衡后不做。
3. **"塞得进一个上下文窗口吗"靠模型判断。** 没有可靠算法，
   只能靠对代码库规模的估计。判断错了，代价是多写一次 spec 或少一次综合。
4. **触发依赖描述匹配。** 措辞不同可能不命中，所以提供 `AGENTS.md` 兜底。
